# AI利用記録: Point#add テストレビュー

## 概要

`Point`クラスの`add`メソッドに対するテストコードを、Claudeとのやり取りを通じて作成・レビューした記録。

## 対象コード

```typescript
export class Point {
  x: number;
  y: number;

  constructor(x: number, y: number) {
    this.x = x;
    this.y = y;
  }

  add(point: Point) {
    this.x += point.x;
    this.y += point.y;
  }
}
```

## やり取りの流れ

### 1. 初回テストのレビュー

最初は正の数のみを足す1ケースのみのテストを提示。以下の指摘を実施:

- `let point` → `const point`(再代入していないため)
- テストケースが1つだけでは不十分

### 2. 追加すべきテストケースの提案

以下4パターンを提案:

1. **正の数の加算** — 基本の正常系
2. **負の数の加算** — 符号によるロジックのバグを検出
3. **ゼロの加算(恒等元)** — 何もしないケースで、更新処理自体が機能していることを確認
4. **自分自身を自分に加算** — `this`と引数が同一参照の場合の副作用(プロパティ更新順序による事故)を検証

### 3. `toEqual` vs `toStrictEqual`

`toStrictEqual`を推奨。理由:

- `toEqual`はprototype(クラス)を無視するため、`Point`インスタンスかどうかを保証できない
- `undefined`プロパティの扱いが異なり、将来のプロパティ追加に対する安全弁になる

### 4. テストケース選定の思考プロセスを言語化

- 正常系を1つ用意して土台を作る
- 入力の符号バリエーション(正/負)を疑う
- 0のような特別な値(恒等元)を検討する
- 実装の構造(`this.x +=`と`this.y +=`が2行に分かれている点)から、状態共有・順序依存のバグが起きそうな箇所(セルフ加算)を狙う

「入力の境界」×「実装から見える危険ポイント」の掛け算でケースを洗い出す、という方針。
